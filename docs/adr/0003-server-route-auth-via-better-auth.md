# ADR-0003: Server-route authentication via better-auth

- **Status:** Accepted
- **Date:** 2026-05-02

## Context

Memento began as a fully client-side PWA: Capture, Inbox, and storage
all live in the browser (localStorage, Web Speech). No server
functionality means no access control boundary is needed — every user
operates on their own device, and "auth" is moot.

The product is now introducing features that require a server:
LLM-backed processing of Entries, sync across devices, usage metering.
The instant a single `/api/*` endpoint does real work on behalf of a
specific person, we need a way to (a) identify the caller, (b) reject
strangers, and (c) do so without compromising Capture — the offline,
zero-friction thought-offload that defines the product.

We also need this to be operator-controlled: the app is not open to
the public. Access is gated by an explicit allowlist of email
addresses that the operator rotates out-of-band.

The shape of the constraint, restated:

1. **Server routes need gates; the PWA does not.** The letterbox
   shell and Capture must remain prerendered and anonymous.
2. **Access is allowlisted, not invited.** Sign-up is not a thing;
   only known emails get through.
3. **Deny-by-default for new routes.** A future contributor adding an
   `/api/*` handler should not be able to ship it open by accident.

## Decision

Adopt **better-auth** with the **Google social provider**, backed by
a **Cloudflare D1** database (`memento-auth`) via the
`drizzleAdapter`. Schema generated from the better-auth config by
`@better-auth/cli`; migrations generated by `drizzle-kit`.

Gate server routes with an **opt-in** `requireUser(event)` helper
from `$lib/server/auth`. Enforce deny-by-default with a
**route-coverage test** (`src/lib/server/route-coverage.test.ts`)
that walks `src/routes/api/**/+server.ts` and fails CI for any file
that neither calls `requireUser` nor matches a path in
`PUBLIC_API_ROUTES` (currently `/api/debug-log` and the `/api/auth`
namespace).

Enforce the **email allowlist twice**:

1. In `databaseHooks.user.create.before` — rejected accounts never
   get a `user` row or a session cookie.
2. In `requireUser` — re-parses `EMAIL_ALLOWLIST` on every request,
   so removing someone from the env takes effect on the next call
   with no D1 cleanup.

Surface auth through a small **AuthChip** absolutely-positioned
inside the Capture pane's `<section>` (top-right, scrolls away with
the section). No `/login` page. OAuth callback errors redirect the
browser to `/?auth_error=<reason>`; `+layout.svelte` consumes the
param on mount, fires a toast via the existing `toast-store`, and
strips the param with `history.replaceState` so reloads do not
re-toast.

Session cookie: 30-day expiry with 1-day sliding `updateAge`,
`HttpOnly`, `Secure` in prod, `SameSite=Lax`, `Path=/`. The long
window is chosen deliberately to be compatible with a future
offline-cached-cookie flow — a user returning after two weeks
offline still authenticates on their next online request.

## Consequences

**Positive**

- **Capture stays sacred.** Root layout keeps `prerender = true`;
  offline Capture is unchanged; the chip is a 32px corner element
  that does not own any gesture geometry.
- **Deny-by-default is mechanically enforced.** A new unprotected
  `/api/*` endpoint fails `npm test` with a message naming the file
  and both ways to fix it (`requireUser` or `PUBLIC_API_ROUTES`).
- **Allowlist is the single source of truth.** Env-var-driven, no
  admin UI, revocation is a config change + deploy.
- **D1 dependency is opt-in per-route.** Public routes (e.g.
  `/api/debug-log`) do not touch D1 at all; the auth layer is only
  instantiated when a protected route asks for it.
- **Future app-wide auth can layer on top.** The cookie settings
  and session shape are compatible with a future hooks-level
  `requireUser` without reshaping any storage.

**Negative**

- **Two allowlist checks** (create-hook + per-request) means the
  allowlist parser runs on every protected request. Cheap (a `Set`
  lookup against a small parsed set) but not free. The alternative
  — relying only on the create-hook — would force a DB-cleanup side
  channel to revoke access, which is strictly worse.
- **Removed users leave session rows in D1.** A user whose email is
  removed from the allowlist cannot pass `requireUser`, but their
  row persists until natural expiry. Acceptable for correctness; a
  cleanup pass can be added if it ever becomes a real concern.
- **Route-coverage test uses a text match.** We grep for
  `requireUser` rather than AST-parsing. False positives (a comment
  mentioning the name without calling it) are possible in principle;
  the alternative is machinery far heavier than the invariant
  warrants.
- **No `/login` page means no graceful degradation** for clients
  with JS disabled. Acceptable — the whole product is a JS-heavy
  PWA; no-JS is not a supported mode.

## Alternatives considered

- **Lucia.** Lightweight, good D1 story. Rejected because
  better-auth ships first-class Google OAuth + the
  `databaseHooks.user.create.before` seam we use for the allowlist.
  Doing the same with Lucia would mean hand-writing the OAuth
  callback and the user-creation gate.
- **Auth.js (NextAuth).** Rejected: SvelteKit + Cloudflare Workers
  + D1 is a rough combination for Auth.js; the adapter story is
  less mature than better-auth's Drizzle adapter.
- **Gating the entire app behind auth.** Rejected. Capture is the
  sacred path; it must work offline, instantly, without a round
  trip. Gating the shell would force a flash on every cold load and
  break the "capture first, process later" promise.
- **Blanket session population in `hooks.server.ts` with route-level
  opt-out.** Rejected on two grounds: (a) it would cost a D1 read
  on every public request (e.g. `/api/debug-log`), and (b) opt-in
  is safer by construction because forgetting to opt out of the
  hook is a silent performance bug, whereas forgetting to opt in to
  `requireUser` is a loud CI failure.
- **A dedicated `/login` route.** Rejected. The chip + toast
  combination has less surface (no new route, no redirect-after-
  sign-in handling, no "already signed in, go away" branch) and
  matches the letterbox-framed UI better.
- **POST-based OAuth anchor (plain `<a href>`).** Tried and
  rejected: better-auth's `/sign-in/social` endpoint is POST-only
  (it sets CSRF state before redirecting). The chip uses the client
  SDK's `signIn.social()` instead; documented in a code comment.

## Re-visit when

- A second OAuth provider is needed. The `AuthSecrets` shape and
  the chip state both assume a single provider; both would need to
  grow.
- App-wide (offline-cached) auth becomes a product requirement.
  That work should layer on top of this slice, not replace it —
  the session cookie settings were chosen for compatibility.
- The allowlist outgrows env-var management (rotating it becomes
  painful, or we want per-user metadata). At that point a minimal
  admin UI or a D1-backed allowlist table is the next step.
- Service-worker-intercepted fetches land. The invariant
  "SW replays preserve credentials" (see `CONTEXT.md`) must be
  verified in code at that point.
